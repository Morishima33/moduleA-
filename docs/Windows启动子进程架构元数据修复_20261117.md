# Windows启动子进程的真实架构元数据

## 问题与边界

已证当前自动化启动环境缺PROCESSOR_ARCHITECTURE，cli 3.6.5的Windows清理函数getenv后未判空即strcmp，
导致R已完成计算后0xc0000005。实际OS/进程x64，补真实AMD64的隔离A/B和原完整R范围回归均通过。
仅给测试补变量不能保证以后通过统一入口启动的工作台和worker继承完整元数据。

本轮只在统一launcher.start_service实际新建子进程时修补其环境副本，不改父进程或系统环境。
Windows且该值缺失/空白时，调用标准GetNativeSystemInfo核真实主机架构再填入；不凭Python位数、
空的同类环境变量或固定AMD64猜测。不冒写ARM64去跳过清理。已有非空值保持，macOS/Linux不增加Windows变量。
核查失败或架构未知必须在创建子进程前明确拒绝，不发起无法核对的新服务。
复用就绪服务、status、stop及科学流程均不因此启动额外程序或改状态；旧服务不热换。

改系统全局变量会扩大影响，修改R/cli或忽略退出码会破坏原约定，本轮均不采用。
复用正常子进程环境继承，标准库小型适配，不新增依赖、队列、数据库或科学协议。
统一modulea.cmd/modulea.command入口由launcher执行，新启动的后续worker按原机制继承；
直接手工serve或旧入口的实际环境仍须独立核对，不能据此宣称所有入口/所有机器都已验证。

## 执行与验证

1. 从原start_service入口捕获实际传给Popen的env，父环境缺失时先复现子环境缺失；不启动真实服务。
2. 新增独立环境适配，只给待启动子进程的副本填真实元数据，launcher最小接线。
3. 测试已有值保留、空值、未知/失败拒绝、非Windows不调用API、父环境不改；
   实际Windows原生API读取、同一R/cli原件在构造的子环境下退出0。
4. 使用既有临时数据目录做真实服务启动/复用/状态/正常停止；实际用户8780和原SCI保持不动。
5. 完成相关回归、自审、独立复审及精确上传；生产部署和Mac实机分别记录。

## 当前验证事实

原启动入口捕获Popen.env时，缺失变量实际为None而真实Windows API读为AMD64，先红；接线后通过。
新环境适配、实际R清理、原隔离服务长中文/长路径启动—复用—状态—正常停止及CMD共18项通过52.032秒。
通过子环境适配启动隔离回归（不在外层手写架构值），公开A05图件/独立决定/当前模块API保护，
及实际HTTP提交、真实后台worker/R统计/结果读回共2项通过62.065秒。父环境保持，未安装或改R/cli。
仅prepare资料不使旧图失效，confirm后科学运行保持而旧范围投影停止；旧图件原件仍可读。
独立静态复审未发现Important，建议的prepare前后隔离断言已纳入实际复跑。
当前实际8780与原SCI均未重启或热换；这批隔离技术验证不代表已部署、真实病例最终验收或Mac/ARM实机通过。
