# 新登记疾病原件预上传与五库衔接

本阶段补齐首次新建研究后GeneCards／OMIM原件的网页预上传入口。无需先签署A00复核，系统实际核查登记后保存本研究原件；上传本身不批准登记、不生成A02候选、不启动科学批次。

## 已实现及页面入口

研究登记页“打开统一执行与续做”→“补齐疾病五库原件”→“先保存GeneCards／OMIM原件”。独立真实资料流程测试预览位于 `http://127.0.0.1:19886`，正式服务未重载；旧服务不声明新能力时不显示或请求新上传入口。

1. 选择GeneCards或OMIM及实际文件格式，选择原始文件。填写原检索词、原获取日期、原数据库版本或快照说明、上传人及依据，保留原引号和导出完整性记录，不默认声称完整。
2. 明确勾选仅预上传，点击“校验并保存本研究原件”。未勾选时按钮不可用；打开、刷新及任务结束不会自动上传。
3. 后台成功后，表中显示实际文件、字节、SHA、原记录日期和版本。版本未知可以据实保存，显示“已预上传；版本待核”，后续五库核验仍按原规则阻断。
4. 原件及必需版本条件齐备后，另行明确获取或核验五库，再发布候选和运行科学批次。新上传改变当前原件绑定，不能静默替换已确认的旧获取请求。

新入口仅适用于新方案、有效且尚未人工批准的A00。原已批准登记继续沿原A02来源入口，不修改旧上传流程。相同请求及同文件只返回原回执；请求号不能复用于不同字节，也不能恢复后来已替换的旧文件。版本过期、人工暂存/退回、回收站、忙碌、文件损坏或明确的疾病检索标题不匹配均有保护。

## 实现与来源链

新增 `A02.system_manual_source.1` 明确上传回执、公开Workflow入口、只读GET、明确multipart POST和独立科学worker。HTTP只检查请求及版本、保存队列字节和实际SHA，原格式解析及疾病身份核查在后台执行；沿用16MiB请求边界，不接受客户端路径、URL、批准、分数或参数覆盖。

实际预上传复用冻结 `intake_sources.stage`，没有复制或改写其科学解析。调用范围内代理load/save：原stage取得原写锁后重核当前输入，在原Workflow.save之前加入同一暂存的明确上传回执，一次保存同时发布原件、暂存版本和回执；没有嵌套同根非重入锁。保存失败时不出现“原件已发布而回执未发布”的半状态，已写但未登记的诊断文件仍保留。

原件继续进入同研究 `current_source_staging` 和完整暂存历史，五库获取沿其既有身份/原件校验读取，完整追溯增加新上传回执及实际原件指纹。新入口没有将未批准登记伪装为approved，未改原标准化、范围筛选、科学参数、状态内核或报告模板。

## 真实全链当前状态与下一步

新的独立真实资料流程例通过实际NLM疾病核对及真实共享参考指纹，尚未进入完整科研链。三库官方采集保存了成功HERB、BATMAN；TCMSP失败点在其靶点对应的UniProt官方查询，HTTP500原响应已归档。核对1308件旧原件及诊断后按原确认补取，已复用成功库和既有请求；后续其他UniProt查询仍遇到500，第二次任务继续按实际失败保留，不反复无条件重试。

两份历史疾病原件的原版本字段为“未知”。本轮保持它们的原日期、原版本与待核状态，没有擅自改为新版本或新检索，也没有用合成例替代真实全链通过。后续继续处理官方请求的暂时失败与可追溯补取，核实疾病原件必要版本条件，再做同批科学全链、报告和统一验收；常规科研复核不代签。
