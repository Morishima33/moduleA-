# 科学恢复的 UTF-8 日志修复

基线：72464cdf61cf4e0b0c5bce4db128f20aa1e6db02。仅修改独立恢复 worker 的日志转写和子进程解释器编码选项，科学规则、原配置、固定名单、模型、工具与评分均不变。

实际 Windows 恢复已通过只读预检并正常进入预算队列，但第一次中文进度的 GBK 字节被按 UTF-8 解码，替代字符又无法写入 GBK 的父日志，触发 UnicodeEncodeError。子进程关闭管道后另存 OSError 失败诊断。已登记适配、原件、失败与检查点保持，不能把此失败称作计算成功。

`-I` 会忽略 PYTHONUTF8 环境变量。新 worker 给隔离科学子进程显式添加 `-X utf8`，并将 worker 的 stdout/stderr 配置为 UTF-8；预算、Job 归属、单研究限制和逐对象恢复完全沿用。未修改原已登记源码副本或归档快照。下一次必须经正常 `resume --authorize-adapter` 显式登记本次不同实现 SHA，不能静默改旧快照或重提并发任务。原 A06 科学协议与参数仍按原绑定核验。

实际隔离子进程测试先复现失败，再验证中文、负号及非 BMP 字符完整穿过 GBK 初始父日志，结果和进度均正确。Windows 恢复相关 22 项测试通过，102.032 秒；含模块代理、预算 Job 后代、损坏/配置变化拒绝和部分区域复用。原机日志 worker_utf8_red.log、worker_utf8_green.log、worker_utf8_regression_final.log 保存在仓库外。

首轮测试启动器错误地使用 -S，导致 CLI 合成工具目录被激活及子测试无 PYTHONPATH；失败日志保留。最终单元测试按其普通 site 模式执行并使用原专用依赖目录、显式源码路径和审计 TEMP。测试中的科学子进程实际使用 -I -S -X utf8。没有安装或修改依赖，没有运行真实 Vina 或生成真实研究 Word。
